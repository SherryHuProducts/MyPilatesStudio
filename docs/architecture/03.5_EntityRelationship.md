# 1. Purpose

This document defines the Entity Relationship Model of MyPilates AI.

It translates the conceptual entities defined in `03_DomainModel.md` into explicit data relationships.

This document answers:

* Which entities exist?
* Which entities own other entities?
* Which relationships are one-to-one?
* Which relationships are one-to-many?
* Which relationships are many-to-many?
* Which relationships require join tables?
* Which entities are Aggregate Roots?
* Which records may be deleted, archived, or preserved?

This document does not define:

* PostgreSQL data types
* Exact database columns
* SQL migrations
* Indexes
* Row Level Security policies
* API endpoints
* Frontend components

Those details belong in `04_Database.md`.

# 2. Relationship Notation

The following notation is used throughout this document.

```text
1:1
One-to-One

1:N
One-to-Many

N:N
Many-to-Many

FK
Foreign Key

PK
Primary Key

Join Table
A table used to represent an N:N relationship

Aggregate Root
The primary entity through which related records are created or modified
```

Example:

```text
Methodology 1:N Curriculum
```

Means:

* One Methodology may contain many Curricula.
* Each Curriculum belongs to one Methodology.

# 3. Relationship Design Principles

## 3.1 Canonical Identity

Every real domain concept must have one canonical identity.

Translations, aliases, methodology-specific variants, and student-specific usage must reference the canonical entity rather than duplicate it.

---

## 3.2 Explicit Relationships

Important business meaning must be represented through explicit relationships.

Professional relationships must not exist only inside:

* Free-text notes
* JSON fields
* AI prompts
* Frontend code

---

## 3.3 Many-to-Many Relationships

An N:N relationship must normally use a join table.

The join table may contain relationship-specific information such as:

* Priority
* Sequence
* Relevance
* Rationale
* Methodology scope
* Knowledge source
* Status

---

## 3.4 Historical Records

Completed teaching records should normally be preserved.

Examples:

* Completed assessments
* Completed lessons
* Final SOAP notes
* AI recommendations
* Instructor decisions

Historical records should not disappear when a related knowledge record is updated.

---

## 3.5 Archive Before Delete

Core entities should usually be archived or deactivated instead of permanently deleted.

Examples:

* Methodology
* Curriculum
* Movement Variant
* Student
* Instructor
* Published knowledge

---

## 3.6 Student Data Isolation

Student-specific information must remain separate from canonical Pilates knowledge.

A student lesson modification must never change the canonical Movement Variant.

---

## 3.7 Methodology Independence

Methodology-specific entities must reference Methodology or Curriculum explicitly.

The database must not assume that STOTT Pilates is the only methodology.

# 5. Knowledge Governance Relationships

## 5.1 Methodology and Curriculum

```text
Methodology 1:N Curriculum
```

Rules:

* One Methodology may contain many Curricula.
* Each Curriculum belongs to one Methodology.
* A Curriculum cannot exist without a Methodology.

Example:

```text
STOTT Pilates
└── Reformer Essential
```

Foreign key direction:

```text
Curriculum.methodology_id
    → Methodology.id
```

Aggregate Root:

```text
Methodology
```

Deletion behavior:

* A Methodology with published Curricula should not be permanently deleted.
* It should be archived or marked inactive.
* A Curriculum should not be deleted if historical lessons reference it.

---

## 5.2 Curriculum and Curriculum Level

```text
Curriculum 1:N Curriculum Level
```

Rules:

* One Curriculum may contain multiple levels.
* Each Curriculum Level belongs to one Curriculum.
* Level names are scoped to their Curriculum.

Foreign key direction:

```text
CurriculumLevel.curriculum_id
    → Curriculum.id
```

Example:

```text
Reformer
├── Essential
├── Intermediate
└── Advanced
```

---

## 5.3 Methodology and Teaching Framework

```text
Methodology 1:N Teaching Framework
```

Rules:

* One Methodology may define multiple Teaching Frameworks.
* Each Teaching Framework belongs to one Methodology.
* Internal MyPilates frameworks may belong to an internal methodology namespace or framework owner.

Foreign key direction:

```text
TeachingFramework.methodology_id
    → Methodology.id
```

---

## 5.4 Teaching Framework and Teaching Principle

```text
Teaching Framework 1:N Teaching Principle
```

Rules:

* One Teaching Framework contains multiple Teaching Principles.
* Each Teaching Principle belongs to one Teaching Framework.
* Principle order should be stored within the relationship or principle record.

Foreign key direction:

```text
TeachingPrinciple.teaching_framework_id
    → TeachingFramework.id
```

Example:

```text
STOTT Five Basic Principles
├── Breathing
├── Pelvic Placement
├── Rib Cage Placement
├── Scapular Movement and Stabilization
└── Head and Cervical Placement
```

Aggregate Root:

```text
Teaching Framework
```

---

## 5.5 Knowledge Source Relationships

A Knowledge Source may support many professional entities.

```text
Knowledge Source N:N Movement Variant
Knowledge Source N:N Cue
Knowledge Source N:N Teaching Principle
Knowledge Source N:N Contraindication
Knowledge Source N:N Teaching Rule
```

Recommended join table:

```text
Knowledge Source Reference
```

Conceptual structure:

```text
KnowledgeSourceReference
├── knowledge_source_id
├── target_entity_type
├── target_entity_id
├── source_location
├── relationship_type
└── notes
```

Alternative implementation:

Separate join tables may be used if stronger relational integrity is required.

Examples:

```text
MovementVariantSource
CueSource
TeachingPrincipleSource
ContraindicationSource
```

The final implementation choice belongs in `04_Database.md`.

---

## 5.6 Entity and Translation

Most knowledge entities may have multiple translations.

```text
Domain Entity 1:N Translation
```

Examples:

```text
Movement Concept 1:N Translation
Movement Variant 1:N Translation
Cue 1:N Translation
Teaching Principle 1:N Translation
Equipment 1:N Translation
Condition 1:N Translation
```

A translation belongs to:

* One entity
* One language
* One translation status

Conceptual key:

```text
entity_type
entity_id
language_code
```

Rules:

* One canonical entity may have multiple languages.
* English and Chinese are not separate Movement records.
* A language should have no more than one active approved translation for the same entity and content field.

---

## 5.7 Taxonomy Relationships

A taxonomy term may classify many entities.

```text
Taxonomy Term N:N Domain Entity
```

Recommended join entity:

```text
Entity Taxonomy
```

Conceptual structure:

```text
EntityTaxonomy
├── taxonomy_term_id
├── entity_type
├── entity_id
└── relationship_type
```

Taxonomy terms may also form hierarchies:

```text
Taxonomy Term 1:N Child Taxonomy Term
```

Example:

```text
Equipment
└── Apparatus
    └── Reformer
```

# 6. Movement Knowledge Relationships

## 6.1 Movement Concept and Movement Variant

```text
Movement Concept 1:N Movement Variant
```

Rules:

* One Movement Concept may have many Movement Variants.
* Every Movement Variant belongs to one Movement Concept.
* The Movement Concept represents shared identity.
* The Movement Variant represents a teachable implementation.

Foreign key direction:

```text
MovementVariant.movement_concept_id
    → MovementConcept.id
```

Example:

```text
Movement Concept:
Footwork

Movement Variants:
├── STOTT Parallel Heels
├── STOTT Parallel Toes
├── STOTT Small V Position
└── Future Polestar Footwork Variant
```

Aggregate Root:

```text
Movement Variant
```

The Movement Concept is a canonical classification entity.

---

## 6.2 Movement Variant and Methodology

```text
Methodology 1:N Movement Variant
```

Rules:

* A methodology-specific Movement Variant belongs to one Methodology.
* A methodology-neutral internal Movement Variant may use a designated internal methodology or nullable methodology policy.
* Methodology attribution must be explicit.

Foreign key direction:

```text
MovementVariant.methodology_id
    → Methodology.id
```

---

## 6.3 Movement Variant and Curriculum

A Movement Variant may appear in multiple Curricula.

A Curriculum contains multiple Movement Variants.

```text
Movement Variant N:N Curriculum
```

Join table:

```text
Curriculum Movement
```

Conceptual structure:

```text
CurriculumMovement
├── curriculum_id
├── movement_variant_id
├── curriculum_level_id
├── sequence_group
├── sequence_order
├── required_status
└── notes
```

Rules:

* Curriculum order belongs in the join table.
* Curriculum-specific naming or notes must not overwrite the canonical Movement Variant.
* A Movement Variant must not be duplicated solely because it appears in more than one Curriculum.

---

## 6.4 Movement Variant and Equipment

One Equipment type may support many Movement Variants.


```text
MovementEquipment

├── quantity
```

* Primary
* Required

* Alternative

## 6.5 Movement Variant and Equipment Configuration


## 6.14 Movement Progression Relationships

Movement progression is a self-referencing relationship.

```text
Movement Variant N:N Movement Variant
```

Join table:

```text
Movement Relationship
```

Conceptual structure:

```text
MovementRelationship
├── source_movement_variant_id
├── target_movement_variant_id
├── relationship_type
├── methodology_id
├── rationale
└── status
```

Possible relationship types:

* Progresses to
* Regresses to
* Prepares for
* Alternative to
* Similar to
* Requires competency in

Rules:

* Source and target cannot be identical.
* The relationship direction must be explicit.
* A progression must include rationale.
* Methodology-specific progressions must retain methodology attribution.

* Draft phases may be deleted.
* Published phases should be versioned with the Movement Variant.

# 8. Student Relationships

## 8.1 Studio and Student

```text
Studio 1:N Student
```

MVP rule:

* Each Student belongs to one Studio.

Future option:

```text
Studio N:N Student
```

may be considered if cross-studio student relationships become necessary.

For Version 1, use `1:N`.

---

## 8.2 Student and Student Goal

```text
Student 1:N Student Goal
```

Rules:

* A Student may have multiple current and historical Goals.
* Each Student Goal belongs to one Student.
* Goals should be archived or completed rather than deleted.

---

## 8.3 Student Goal and Training Goal

A Student Goal may map to a standardized Training Goal.

```text
Training Goal 1:N Student Goal
```

A Student Goal may also contain personalized wording.

Example:

```text
Canonical Training Goal:
Improve Balance

Student Goal:
Feel more confident walking downstairs
```

---

## 8.4 Student and Student Preference

```text
Student 1:N Student Preference
```

Preferences may include:

* Cue preference
* Language preference
* Tactile cue preference
* Exercise preference
* Learning style

---

## 8.5 Student and Student Health Profile

```text
Student 1:1 Student Health Profile
```

Rules:

* Each Student has zero or one active Health Profile.
* Historical changes may be stored through versioning or related history records.
* The Health Profile is a dependent part of the Student aggregate.

---

## 8.6 Student and Student Condition

```text
Student 1:N Student Condition
```

Each Student Condition connects the Student to one canonical Condition.

```text
Condition 1:N Student Condition
```

Therefore:

```text
Student N:N Condition
```

is implemented through:

```text
Student Condition
```

Conceptual structure:

```text
StudentCondition
├── student_id
├── condition_id
├── status
├── source_type
├── onset_date
├── clearance_status
└── notes
```

---

## 8.7 Student and Consent Record

```text
Student 1:N Consent Record
```

Rules:

* A Student may grant, renew, or revoke multiple consent types.
* Consent history must be preserved.
* The current consent state is derived from the latest valid record.

---

## 8.8 Student and Equipment Access

```text
Student N:N Equipment
```

```text
Student Equipment Access
```

Conceptual structure:

```text
StudentEquipmentAccess
```


Join table:

```text
Role Permission
```

This allows permissions to change independently from Role definitions.

## 11.6 Recommendation and Evidence

Evidence may support the entire Recommendation or a specific Recommendation Item.

```text

```

```text

```

Conceptual structure:

```text

├── recommendation_id
├── recommendation_item_id
├── evidence_entity_type
├── evidence_entity_id
├── knowledge_version_id

└── explanation
```

Evidence may reference:

* Student Goal
* Assessment Finding
* Assessment Observation
* Lesson Record
* Session Feedback
* Movement Variant
* Teaching Rule
* Contraindication
* Teaching Principle
* Progression Relationship

Rules:

* Evidence references must be immutable for historical recommendations.
* Knowledge version should be retained when relevant.
* Evidence must distinguish knowledge from student context.

---

## 11.7 Recommendation and Instructor Decision

```text
Recommendation 1:N Instructor Decision
```

For MVP, one current decision may be used.

Multiple decision records preserve review history.

Possible decisions:

* Accepted
* Modified
* Rejected
* Deferred

Each Instructor Decision belongs to one Instructor.

```text
Instructor 1:N Instructor Decision
```

---

## 11.8 Recommendation and Lesson Plan

A Lesson Recommendation may create or support one Lesson Plan.

```text
Recommendation 1:0..1 Lesson Plan
```

A Lesson Plan may reference its originating Recommendation:

```text
LessonPlan.recommendation_id
    → Recommendation.id
```

Rules:

* The Lesson Plan becomes an instructor-controlled teaching object.
* Editing a Lesson Plan does not rewrite the original Recommendation.
* Recommendation and final plan differences should remain traceable.

---

## 11.9 AI Model Execution and Recommendation

```text
AI Model Execution 1:N Recommendation
```

or, for simple MVP implementation:

```text

```

Recommended flexible design:

* One execution may produce multiple candidate Recommendations.
* Every Recommendation references one execution.

# 15. Delete and Archive Rules

## 15.1 Cascade Delete Allowed

Cascade deletion may be allowed for dependent draft records that have no independent historical meaning.

Examples:

```text
Draft Lesson Plan
└── Draft Lesson Blocks
    └── Draft Lesson Exercises
```

```text
Draft Recommendation
└── Recommendation Items
```

---

## 15.2 Cascade Delete Not Allowed

Cascade deletion should not remove historical teaching or knowledge records.

Examples:

* Deleting a Student must not automatically delete completed Lessons.
* Deleting a Curriculum must not delete Movement Variants.
* Deleting a Movement Variant must not delete completed Lesson Exercises.
* Deleting an Instructor must not delete approved SOAP Notes.
* Deleting an AI Model Execution must not delete Recommendations.

---

## 15.3 Archive Required

The following entities should normally support archive or inactive status:

* Studio
* Instructor
* Student
* Methodology
* Curriculum
* Teaching Framework
* Teaching Principle
* Movement Concept
* Movement Variant
* Cue
* Equipment
* Condition
* Contraindication
* Assessment Template
* Taxonomy Term

---

## 15.4 Historical References

When an entity is archived:

* Historical records remain readable.
* New records should not select it by default.
* AI retrieval should exclude it unless historical context is required.
* Existing foreign key references remain valid.

# 20. ER Model Validation Rules

Before adding a relationship, confirm:

1. Is the relationship real in the Pilates domain?
2. Is it `1:1`, `1:N`, or `N:N`?
3. Does the relationship contain its own business data?
4. Does it require a join table?
5. Which entity owns the relationship?
6. Should deletion cascade?
7. Must historical references survive?
8. Is the relationship methodology-specific?
9. Is the relationship student-specific?
10. Does it affect safety?
11. Does it require versioning?
12. Can the same relationship support Polestar later?

---

# 21. Final Principle

The ER Model connects four different worlds:

```text
Professional Knowledge
Student Context
Teaching History
AI Recommendations
```

These worlds must be connected, but never confused.

Professional knowledge defines what is known.

Student data defines who is being taught.

Teaching records define what occurred.

AI recommendations define what was suggested.

The database must preserve these distinctions through explicit, traceable relationships.
